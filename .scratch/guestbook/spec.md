# Spec: 미니 방명록

Status: ready-for-agent

## Problem Statement

방문자가 회원가입이나 로그인 없이 가볍게 이름과 메시지를 남기고, 다른 사람들이 남긴 방명록 글을 한눈에 보고 싶다. 동시에 글쓴이는 자기가 쓴 방명록 글을 나중에 고치거나 지울 수 있어야 하지만, 다른 사람이 그 글을 함부로 고치거나 지워서는 안 된다. 계정이 없으므로 "내 글"임을 확인할 수단이 필요하다.

## Solution

한 페이지짜리 미니 방명록. 누구나 이름·메시지·비밀번호를 입력해 방명록 글을 남기고, 전체 방명록 글을 작성 시각의 최신순으로 본다. 각 방명록 글의 수정·삭제는 그 글을 쓸 때 정한 비밀번호를 아는 사람(글쓴이)만 할 수 있다. 비밀번호가 틀리면 요청은 거부되고, 그 사실이 해당 방명록 글 바로 아래에 안내된다. 페이지 왼쪽 상단에는 서비스 제목과 개발자 정보(박시현 · 202404222)가 배너처럼 크게 표시된다. 서비스는 Vercel에 배포되어 누구나 접속할 수 있다.

## User Stories

1. 방문자로서, 이름·메시지·비밀번호를 입력해 방명록 글을 남기고 싶다. 그래야 회원가입 없이도 흔적을 남길 수 있다.
2. 방문자로서, 페이지에 들어오자마자 전체 방명록 글 목록을 보고 싶다. 그래야 다른 사람들이 남긴 메시지를 읽을 수 있다.
3. 방문자로서, 목록이 작성 시각의 최신순으로 정렬되길 원한다. 그래야 가장 최근 방명록 글을 먼저 볼 수 있다.
4. 방문자로서, 각 방명록 글의 이름·메시지·작성 시각을 함께 보고 싶다. 그래야 누가 언제 남긴 글인지 알 수 있다.
5. 방문자로서, 작성 시각이 한국 시간 기준 `YYYY-MM-DD HH:mm` 형식으로 보이길 원한다. 그래야 시각을 헷갈리지 않고 읽을 수 있다.
6. 방문자로서, 방명록 글을 남기면 목록 맨 위에 바로 나타나길 원한다. 그래야 작성이 성공했음을 확인할 수 있다.
7. 방문자로서, 이름·메시지·비밀번호 중 하나라도 비어 있거나 공백뿐이면 작성이 거부되고 이유가 안내되길 원한다. 그래야 빈 방명록 글이 쌓이지 않는다.
8. 방문자로서, 이름은 1–20자, 메시지는 1–500자, 비밀번호는 4–50자 범위를 벗어나면 안내를 받고 싶다. 그래야 어떤 입력이 허용되는지 알 수 있다.
9. 방문자로서, 입력값의 앞뒤 공백이 자동으로 잘리길 원한다. 그래야 실수로 넣은 공백이 저장되지 않는다.
10. 방문자로서, 검증에 실패해도 입력하던 내용이 지워지지 않길 원한다. 그래야 다시 처음부터 입력하지 않아도 된다.
11. 방문자로서, 다른 사람과 같은 이름으로 방명록 글을 남길 수 있길 원한다. 그래야 이름이 겹친다는 이유로 막히지 않는다.
12. 글쓴이로서, 내 방명록 글의 "수정"을 누르면 그 자리에 메시지 입력칸과 비밀번호 입력칸이 펼쳐지길 원한다. 그래야 페이지를 떠나지 않고 수정할 수 있다.
13. 글쓴이로서, 수정 입력칸에 기존 메시지가 미리 채워져 있길 원한다. 그래야 일부만 고칠 수 있다.
14. 글쓴이로서, 올바른 비밀번호를 입력하면 메시지가 수정되길 원한다. 그래야 오타나 내용을 고칠 수 있다.
15. 글쓴이로서, 수정할 수 있는 것은 메시지뿐이고 이름은 바뀌지 않길 원한다. 그래야 방명록 글의 주체가 유지된다.
16. 글쓴이로서, 수정해도 작성 시각과 목록에서의 위치가 바뀌지 않길 원한다. 그래야 수정이 새 글처럼 보이지 않는다.
17. 방문자로서, 수정된 방명록 글에 "(수정됨 · 수정 시각)"이 작게 표시되길 원한다. 그래야 원래 내용에서 바뀌었음을 알 수 있다.
18. 글쓴이로서, 비밀번호가 틀리면 수정이 거부되고 해당 방명록 글 아래에 "비밀번호가 일치하지 않습니다"가 빨간 글씨로 표시되길 원한다. 그래야 왜 실패했는지 알 수 있다.
19. 글쓴이로서, 비밀번호가 틀려도 입력하던 새 메시지가 유지되길 원한다. 그래야 비밀번호만 다시 입력하면 된다.
20. 글쓴이로서, 수정한 메시지도 1–500자 검증을 똑같이 받길 원한다. 그래야 수정으로 빈 메시지가 생기지 않는다.
21. 글쓴이로서, 수정에 성공하면 입력칸이 닫히고 목록에 새 메시지가 반영되길 원한다. 그래야 결과를 바로 확인할 수 있다.
22. 글쓴이로서, 수정 도중 "취소"로 입력칸을 닫을 수 있길 원한다. 그래야 마음이 바뀌면 그만둘 수 있다.
23. 글쓴이로서, 내 방명록 글의 "삭제"를 누르면 그 자리에 비밀번호 입력칸이 펼쳐지길 원한다. 그래야 비밀번호 입력이 곧 삭제 확인 역할을 한다.
24. 글쓴이로서, 올바른 비밀번호를 입력하면 방명록 글이 삭제되고 목록에서 사라지길 원한다. 그래야 원치 않는 글을 지울 수 있다.
25. 글쓴이로서, 비밀번호가 틀리면 삭제가 거부되고 해당 방명록 글 아래에 "비밀번호가 일치하지 않습니다"가 표시되길 원한다. 그래야 삭제되지 않았음을 알 수 있다.
26. 방문자로서, 비밀번호를 모르는 방명록 글은 수정·삭제할 수 없길 원한다. 그래야 내 글도 남에게 훼손되지 않는다.
27. 글쓴이로서, 다른 탭 등에서 이미 삭제된 방명록 글을 수정·삭제하려 하면 "이미 삭제된 글입니다"가 안내되고 목록이 새로 고쳐지길 원한다. 그래야 비밀번호를 잘못 친 것으로 오해하지 않는다.
28. 방문자로서, 한 번에 하나의 방명록 글에서만 수정/삭제 입력칸이 열려 있길 원한다. 그래야 화면이 어지럽지 않다.
29. 방문자로서, 비밀번호 입력칸이 가려진(password) 입력으로 보이길 원한다. 그래야 옆 사람에게 비밀번호가 노출되지 않는다.
30. 방문자로서, 내가 입력한 비밀번호가 평문으로 저장되지 않길 원한다. 그래야 다른 곳에서 쓰는 비밀번호를 넣었더라도 유출 위험이 줄어든다.
31. 방문자로서, 방명록 글이 하나도 없을 때 "아직 방명록 글이 없습니다" 같은 빈 상태 안내를 보고 싶다. 그래야 페이지가 고장 난 것으로 오해하지 않는다.
32. 방문자로서, 제출 중에는 버튼이 비활성화되어 중복 제출이 막히길 원한다. 그래야 같은 방명록 글이 두 번 올라가지 않는다.
33. 방문자로서, 페이지 왼쪽 상단에 "미니 방명록" 제목과 개발자 박시현 · 202404222가 배너처럼 크게 보이길 원한다. 그래야 누가 만든 서비스인지 바로 알 수 있다.
34. 방문자로서, 휴대폰 화면에서도 가로 스크롤 없이 쓸 수 있길 원한다. 그래야 어디서나 방명록을 쓸 수 있다.
35. 방문자로서, 긴 메시지나 줄바꿈이 포함된 메시지가 깨지지 않고 표시되길 원한다. 그래야 여러 줄 메시지도 읽을 수 있다.
36. 방문자로서, 메시지에 HTML이나 스크립트를 넣어도 그대로 텍스트로 표시되길 원한다. 그래야 악의적인 방명록 글이 페이지를 망가뜨리지 않는다.
37. 방문자로서, 배포된 주소로 접속해 같은 기능을 쓰고 싶다. 그래야 로컬 환경 없이도 방명록을 이용할 수 있다.

## Implementation Decisions

- **용어**: GLOSSARY.md의 용어(방명록 글, 메시지, 이름, 비밀번호, 글쓴이, 작성 시각, 수정 시각)를 따른다. 코드에서 방명록 글은 `Entry`로 부른다.
- **저장소**: Neon Postgres에 ORM 없이 순수 SQL로 접근한다. 이미 설치된 Neon serverless 드라이버와 환경 변수 `DATABASE_URL`을 사용한다. 로컬 개발과 Vercel 배포는 같은 DB를 공유한다.
- **스키마**: 테이블 `entries` 하나.
  - `id`: 자동 증가 정수 기본키
  - `name`: text, not null
  - `message`: text, not null
  - `password_hash`: text, not null (salt 포함 저장 형식)
  - `created_at`: timestamptz, not null, 기본값 now()
  - `updated_at`: timestamptz, null 허용 (수정된 적 없으면 null)
  - 목록 정렬은 `created_at DESC, id DESC`.
- **스키마 적용**: 스키마를 SQL 파일로 두고, 이를 `DATABASE_URL`에 적용하는 npm 스크립트(`db:setup`)를 둔다. 스크립트는 재실행해도 안전하게(`IF NOT EXISTS`) 작성한다. 런타임에 테이블을 생성하지 않는다.
- **비밀번호**: Node 내장 `crypto.scrypt`로 무작위 salt와 함께 해시하여 저장하고, 검증 시 `timingSafeEqual`로 비교한다. 추가 의존성 없음. 비밀번호와 해시는 어떤 응답이나 클라이언트 데이터에도 포함되지 않는다.
- **guestbook 모듈 (핵심, 깊은 모듈)**: 방명록 도메인 규칙 전부(검증, 해싱, 권한 확인, SQL)를 캡슐화한다. SQL 실행기를 의존성으로 주입받는다(운영: Neon, 테스트: PGlite). 공개 인터페이스는 네 연산:
  - 목록 조회 → 방명록 글 배열 (id, 이름, 메시지, 작성 시각, 수정 시각; 비밀번호 해시 제외)
  - 작성(이름, 메시지, 비밀번호) → `ok`(생성된 방명록 글) | `invalid`(필드별 오류)
  - 메시지 수정(id, 새 메시지, 비밀번호) → `ok` | `invalid` | `wrong-password` | `not-found`
  - 삭제(id, 비밀번호) → `ok` | `wrong-password` | `not-found`
  - 예외를 던지지 않고 판별 가능한(discriminated) 결과 타입을 반환한다. DB 장애 같은 예기치 못한 오류만 예외로 전파된다.
- **검증 규칙** (모듈 안에서 단일 정의, 클라이언트는 같은 규칙을 재사용해 즉시 피드백):
  - 앞뒤 공백을 잘라낸 뒤 판단한다.
  - 이름 1–20자, 메시지 1–500자, 비밀번호 4–50자.
  - 비밀번호도 앞뒤 공백을 잘라낸 값으로 길이를 검사하고 해싱·비교한다(작성과 수정·삭제 시 동일 처리).
- **서버 호출**: 작성·수정·삭제는 Server Actions로 처리한다. Action은 폼 데이터를 guestbook 모듈에 넘기고, 결과 타입을 화면 상태(성공/필드 오류/비밀번호 불일치/이미 삭제됨)로 변환한 뒤 목록을 재검증(revalidate)하는 얇은 층이다. 별도 REST API는 만들지 않는다.
- **화면**: 단일 페이지.
  - 왼쪽 상단 배너: 큰 "미니 방명록" 제목 + 눈에 띄는 배지로 "박시현 · 202404222".
  - 그 아래 작성 폼(이름, 메시지 textarea, 비밀번호 password 입력).
  - 그 아래 최신순 전체 목록(페이지네이션 없음). 각 방명록 글에 "수정"/"삭제" 버튼, 누르면 그 자리에 인라인 입력칸이 펼쳐진다. 한 번에 하나만 열린다.
  - 비밀번호 불일치: 해당 방명록 글 아래 빨간 안내 "비밀번호가 일치하지 않습니다", 입력값 유지.
  - 이미 삭제됨: "이미 삭제된 글입니다" 안내 후 목록 새로 고침.
  - 수정된 방명록 글에는 "(수정됨 · 수정 시각)" 표시.
  - 시각 표시는 `Asia/Seoul` 기준 `YYYY-MM-DD HH:mm`.
  - 메시지는 텍스트로 렌더링하고 줄바꿈을 보존한다(HTML 해석 금지).
- **Next.js 버전 주의**: 이 프로젝트는 Next.js 16.3이다. 구현 전에 `node_modules/next/dist/docs/`의 해당 가이드(Server Actions, 캐싱/재검증, 폼)를 확인하고 deprecation 안내를 따른다.
- **배포**: GitHub 저장소 → Vercel import. Vercel 프로젝트 환경 변수에 `DATABASE_URL` 설정. 저장소 생성, Vercel import, 환경 변수 설정은 사용자가 직접 수행하며, 에이전트는 커밋 정리와 단계 안내를 맡는다.

## Testing Decisions

- **좋은 테스트의 기준**: guestbook 모듈의 공개 인터페이스를 통해 관찰 가능한 동작만 검증한다. 내부 함수, SQL 문자열, 해시 형식 같은 구현 세부는 테스트하지 않는다. 예: "틀린 비밀번호로 삭제하면 `wrong-password`를 받고, 이후 목록 조회에 그 방명록 글이 여전히 있다."
- **테스트 경계**: guestbook 모듈 하나. Server Actions와 UI는 결과 타입을 화면 상태로 바꾸는 얇은 층이므로 자동 테스트 대상이 아니며, 수동 확인한다.
- **도구**: Vitest + PGlite(인메모리 Postgres). 각 테스트(또는 파일)는 새 PGlite 인스턴스에 운영과 동일한 스키마 SQL을 적용한 뒤 guestbook 모듈에 주입한다. 실제 Neon DB는 로컬과 배포가 공유하므로 테스트에서 절대 사용하지 않는다.
- **다룰 동작**:
  - 작성 후 목록에 나타나며 작성 시각 최신순으로 정렬된다.
  - 목록 결과에 비밀번호/해시가 포함되지 않는다.
  - 필드별 검증(빈 값, 공백만, 경계 길이 20/21, 500/501, 3/4/50/51자)과 앞뒤 공백 제거.
  - 올바른 비밀번호로 메시지 수정 → 메시지 변경, 수정 시각 설정, 이름·작성 시각·순서 불변.
  - 틀린 비밀번호로 수정/삭제 → `wrong-password`, 데이터 불변.
  - 존재하지 않는(이미 삭제된) id로 수정/삭제 → `not-found`.
  - 올바른 비밀번호로 삭제 → 목록에서 사라짐.
  - 같은 이름의 방명록 글 여러 개가 각자의 비밀번호로만 수정·삭제된다.
- **기존 선례**: 저장소에 테스트가 아직 없다. 이 테스트가 첫 선례가 된다.

## Out of Scope

- 회원가입, 로그인, 세션, 관리자 권한(관리자 일괄 삭제 등)
- 이름 수정, 방명록 글 이력(버전) 보관
- 페이지네이션, 검색, 필터
- 스팸 방지(캡차, 요청 빈도 제한)
- 비밀번호 찾기/재설정
- 이미지·파일 첨부, 댓글/답글, 좋아요
- 로컬/배포 DB 분리(Neon 브랜치)
- UI와 Server Actions에 대한 자동화된 E2E 테스트

## Further Notes

- 로컬과 배포가 같은 DB를 쓰므로, 제출 전에 테스트 목적으로 남긴 방명록 글을 정리해야 한다.
- 비밀번호로 소유를 확인하는 방식은 요구사항에 명시된 것이라 ADR로 남기지 않았다.
